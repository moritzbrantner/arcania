# ADR 0026: Browser Solo matches and a local card workshop

## Status
Accepted

## Decision

GitHub Pages cannot host Axum. `rune-lanes-browser` is a WebAssembly application adapter over `rune-lanes-core`, with no server, auth, database, or network dependency. It selects commands with the existing baseline AI policy and executes them through `GameCommand`; its Player legality projection uses the query facade. Existing hosted flows retain their HTTP adapter. The special `browser-solo` match ID selects the browser adapter explicitly; network failures never silently switch an existing match to local play.

Rules are frozen per Match in the typed `RuneLanesRuleset`, including in compatibility snapshots. Existing constructors and historical snapshots use the current default. The workshop validates bounded numeric rule values and custom `CardDefinition` values in Rust. Custom cards use existing effect semantics and are given to both opening hands so users can try them immediately. They do not alter the hosted card catalog or account deck legality.

Browser persistence is a versioned setup plus ordered accepted commands, replayed through the core on reload. This is an application command journal, not the domain event stream described in ADR 0024. There is no authoritative browser snapshot or silent repair of incompatible saves. One browser Solo match is retained; starting another replaces it. Rules/card presets persist separately, support JSON import/export, and affect new matches only. Local storage write failures roll back the attempted move. These experiments do not award account progression.

The Pages workflow builds the WASM with the pinned wasm-bindgen CLI and runs desktop/mobile tests against the built site at `/arcania/` without a backend. After deployment, it checks the published commit in `deployment.json` and repeats those flows on the public Pages URL. Client-route reloads use Pages' `404.html` fallback; tests require restored state and successful assets even though the document has a 404 status. Presentation assets retain their asset-tooling specs, receipts, revision, and replay verification alongside the intentionally distributed SVG.

## Consequences

Workshop presets may specify independent Player and Opponent recipes of known built-in Card templates. The core validates unique entries, counts from 1 to 30, and totals from the configured opening hand size to 120. Authoring normalization retains a matching system recipe's historical order and otherwise orders custom recipes by template ID, so equivalent counts and seed yield identical deals and Card instance IDs. Missing recipe fields use Balanced Starter, preserving older presets and command journals. The WASM adapter exposes the same configured recipes used by hosted player and AI loadouts; hosted account deck legality remains separate.

Browser users can play against bots without signing in or operating a server. Core rule changes must retain default hosted behavior and have core coverage. Seeded shuffles take the modulus before narrowing to a pointer-sized integer so native and wasm32 hosts agree. Spell and Item AP effect fields serialize as `maxAp` for the client; `max_ap` remains an accepted alias for older persisted data. New effect semantics belong in the core, not in editable JavaScript. A future incompatible engine/journal change must version or migrate browser saves explicitly. Hosted multiplayer, account progression, and server archives still require the backend.

Authored Card test scenarios reuse the core `WorkshopSetup` validation, seeded construction, deck recipes and typed rule configuration. A serializable scenario adds an empty, adjacent-enemy, clustered-enemy, damaged-ally or low-HP-Hero board layout. Starting hands contain the authored Cards; seeded draw piles remain available to test draw effects. The arena omits neutral Buildings and Mana sources, fixture Units take their stats from the existing Stoneguard template, and the low-HP layout sets both Heroes to one HP for healing and defeat tests.

Preparing a scenario constructs its owned initial state once. Independent runs and resets clone that prepared state, preserving private draw piles and RNG state without rereading mutable authoring input. Commands, legality queries, domain events and replay continue to use the existing core facades; there is no scenario-specific rules runtime. This capability is available to core callers independently of the debug-only development scenarios in ADR 0010. Persisted Account draft integration uses the application boundary below; test-arena UI and sharing remain separate deliveries.

Authenticated draft scenarios extend `CardWorkshop` through `POST /api/card-drafts/{draft_id}/scenarios/run`. The request supplies the exact draft version, a core scenario with an empty authored Card list, and ordered side/command pairs. The adapter loads only the Account's owned draft, checks its cached core validation diagnostics and version, then maps its stable catalog identity into an owned experimental Card definition. Supplied alternative Cards are rejected rather than overriding the persisted source.

The authenticated `/workshop/cards` route browses Account-owned persisted Drafts through the hosted Draft API. Official-Card duplication loads the exact compiled revision through the existing transfer endpoint before creating a new Draft with an independent local ID. It preserves the complete definition, including mechanics and taxonomy omitted by the display catalog. React presents stored validation diagnostics without implementing Card semantics. Loading and creation failures retain a recovery path, and leaving the route cancels a pending source load's follow-up creation. Editing sends the complete edited definition with the Draft version through `PATCH /api/card-drafts/{draft_id}`; the response's stored core diagnostics are shown as returned. The client only rejects numbers the API cannot represent (non-integers or values outside the core field's integer range). Unsaved edits are kept per Draft until saved or explicitly discarded; a version conflict offers loading the latest saved version as the new base without dropping them. This Account flow and the anonymous browser-local Workshop use their explicit existing storage adapters.

The prepared draft scenario owns its initial state and command trace independently of SQLite. The route releases the store lock before executing that trace through `EventSourcedMatch` decisions/evolution. Responses include the source draft identity/version, initial/final query projections, domain events and the existing HTTP replay projection. Empty traces preview the initial setup; rejected commands report their index and core error. Runs leave drafts, published history and match archives unchanged, and create no saved scenario lifecycle. Test-arena UI and sharing remain separate deliveries.
