# Exact Card pack manifests

Card pack manifests identify a pack by its stable ID and positive content version, list exact published Card revision IDs, and declare exact versions of dependency packs. The manifest schema version and required ruleset schema version are separate compatibility metadata. Exact references preserve a portable collection's meaning when newer Cards or packs are published; loading a newer available version cannot satisfy a missing reference.

`rune-lanes-core` validates the complete supplied manifest set against a published Card catalog before exposing it through `CardPackCatalog`. Duplicate pack identities fail before content validation; missing references, unknown manifest schemas and incompatible dependency/ruleset versions produce typed diagnostics. Validation visits every supplied manifest without recursively loading dependencies. Manifests contain references; Card definitions remain owned by the existing published catalog. Import/export, content installation and freezing a match's catalog are separate deliveries.

Card taxonomy lives in the existing authored `CardDefinition` and is frozen with its published revision. Faction and element are optional single tags; traits and Card families are ordered, duplicate-free tag lists. Tags use the same lowercase, digit and single interior hyphen grammar as stable Card IDs; no fixed faction or element vocabulary is invented. Invalid values remain editable in drafts and produce field-specific publication diagnostics. Values are preserved without trimming, sorting or inheriting mechanics. Empty taxonomy is omitted on serialization so historical definitions retain their JSON shape.

`CardCatalog::discover` combines all supplied taxonomy fields and returns exact published revisions in identity order, including older matching revisions. Pack manifests continue to refer to those exact revisions instead of copying metadata or selecting a newer revision. Instantiating a match Card omits taxonomy, so tags do not enter gameplay state or replay frames. Content transfer and player-facing search remain separate deliveries.

Single-Card transfer uses a separate versioned document containing one exact `PublishedCardRevision`. Export resolves an exact identity from a supplied `CardCatalog`; it never substitutes the latest revision. Import preparation compares the complete immutable definition, including taxonomy and presentation text, against a supplied destination. The prepared import borrows both inputs, exposes new, already-present or conflicting content, and can produce a new owned catalog without changing the destination. Identical content is idempotent; differing content at the same identity cannot be applied. Account installation and complete-pack transfer remain separate application deliveries.

Transfer parsing reuses the existing published definition validation and rejects unknown fields in the authored Card/revision/effect vocabulary, preventing unsupported content from being silently discarded during a round trip. Existing defaults and documented aliases remain supported. Structural equality on that vocabulary compares complete content without serialization or a second mechanics validator; `CardCatalog::revisions` exposes all exact revisions for constructing the owned result.
